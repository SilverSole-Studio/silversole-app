# 全天步態計算——設計

- 日期：2026-10-31
- 狀態：設計待使用者審閱
- 範圍：只動 App（本 repo）。不動韌體、不動 Supabase、不動 H5 遊戲。
- 依據：雙腳連線（`2026-10-20-double-feet-design.md`）已完成，每隻鞋墊有自己的 `liveTelemetryProvider(soleKey)` 和配對清單上的 `footSide`；雙腳遊戲輸入（`2026-10-22-two-feet-game-input-design.md`）已確認 FSR 讀數可用。

## 使用者已決定的事

| 項目 | 決定 |
|---|---|
| 先做哪塊 | 判斷每一步、步態頁換真數字。資料上雲、AI 白話週報之後再做 |
| 進入方式 | 全天背景自動計算（不是引導式量測） |
| 頭條數字 | 每日走路步數（步速算不出來，換掉） |
| 分期／參考步速帶／建議行動 | 拿掉 |
| 正式版 | 門檻用真人資料校正前先關，只有 debug 版打開 |
| 真人資料 | 目前手上沒有鞋墊，要跟團隊拿；拿到前用自動測試與合成資料開發 |

## 1. 現況

- 步態分頁（`gait_panel.dart`、`gait_panel_t2.dart`）的數字全部來自 `gait_analysis_data.dart` 的 `gaitSnapshot()`，是寫死的範例，頁面頂端有「範例資料・尚未實際量測」橫幅（commit 198ae29）。
- App 沒有判斷步伐、計步、步速的程式。`ble` 裡的「步伐峰值」只用來分辨哪隻鞋墊在哪隻腳。
- 即時資料在 `LiveTelemetryNotifier.updateImuNotifyData` 先經過 `ImuMovingAverageFilter`（10 筆移動平均）才存起來。平均會把腳跟落地的時間點抹平，判斷步伐不能用平均後的值。
- 即時資料本身沒有時間戳，只有 `LiveTelemetryNotifier._stamp()` 的手機時間。程式註解對通知頻率的說法不一致（20 Hz／50 Hz），所以設計一律用時間、不用筆數。
- 每筆即時資料有 3 個 FSR，順序是大拇趾球、小趾球、腳跟（`fixPressureChannels` 已處理這塊板子的通道對調），單位是原始計數。

## 2. 資料流

```
BLE live notify
  → LiveTelemetryNotifier.updateImuNotifyData(raw)
      ├─ (既有) ImuMovingAverageFilter → recentImu → 畫面、遊戲
      └─ (新增) GaitTracker.addSample(soleKey, foot, raw.pressure, now)
             → StepDetector(每隻腳一個) → StepEvent
             → BoutFilter → 走路段落裡的 StepEvent
             → DailyGaitAccumulator → 每小時與 App 進背景時寫入本機
  步態分頁 ← dailyGaitHistoryProvider（讀本機的每日統計）
```

原本的畫面、熱圖、遊戲完全不動。新增的那條線只在功能開關打開時接上（見第 6 節）。

## 3. 模組

全部是純 Dart，不碰藍牙、不碰 Flutter 畫面，可以單獨測試。放在 `lib/core/gait/`。

### 3.1 `StepDetector`（一隻腳一個）

- 輸入：`(DateTime t, List<int> pressure)`。
- 看「腳跟」和「前腳掌（大拇趾球＋小趾球）」兩條壓力。
- **自適應門檻**：不做開機校正。持續追蹤這隻腳最近 5 秒的低點與高點，門檻放在兩者之間，上下各留遲滯區間，避免在門檻附近抖動重複觸發。跟雙腳遊戲輸入「壓力參考值自己適應」是同一個思路。
- 輸出 `StepEvent`：`heelStrike`（總負荷由低轉高的時間）、`toeOff`（由高轉低的時間）。
- 缺資料超過 0.5 秒（斷線、掉封包）就重置狀態，那一步不算。
- 總負荷長時間都很低（鞋墊沒穿、腳懸空）就不輸出任何事件。

### 3.2 `BoutFilter`

- 同一隻腳連續 5 個步幅（≈ 10 步）以上、每個步幅時間在 0.7–2.0 秒之間、相鄰步幅時間變化不超過 40%，才算「在走路」。
- 段落中間超過 2.5 秒沒有落地就結束這個段落。
- 段落未達門檻前的事件先暫存，達標才一起放行；沒達標就丟掉。坐著抖腳、站著換重心、零星幾步因此不計。
- 數值（5 個步幅、0.7–2.0 秒、40%、2.5 秒）是初始值，校正時調整，集中放在一個設定物件裡。

### 3.3 `DailyGaitAccumulator`

只累積走路段落裡的事件，每天一筆，**存統計量，不存原始資料**：

| 欄位 | 用途 |
|---|---|
| 步數 | 單隻鞋墊：落地次數 × 2；兩隻都在線：兩腳落地次數相加 |
| 走路秒數 | 段落時長總和 |
| 每隻腳的站立時間、擺盪時間：總和、筆數 | 站立期／擺盪期比例 |
| 每隻腳的步幅時間：總和、平方和、筆數 | 每步時間變異（變異係數） |
| 雙腳同時著地時間總和（只在兩腳同一段落時） | 雙腳支撐期 |

存平方和就能在不存每一步的情況下算出變異係數，週、月也能把多天合併。

### 3.4 `GaitTracker`

- 依 `soleKey` 管每隻鞋墊的 `StepDetector`，用配對清單的 `footSide` 標左右。沒指定左右的鞋墊照樣算步數，但不進左右對稱。
- 兩隻都在線且都在走路段落時，才計算雙腳支撐期與左右對稱。
- 跨過午夜時把累積結果切到新的一天。

## 4. 存檔

- 沿用 `save_service.dart` 的 shared_preferences，新增一個 `LocalSavableKey`，值是「日期 → 每日統計」的 JSON。
- 保留最近 90 天（季檢視要 12 週），更早的刪掉。
- 寫入時機：每小時一次，加上 App 進背景時（`AppLifecycleState.paused`）。程式被系統砍掉時，最多掉最後一小時。

## 5. 步態頁

### 5.1 指標

| 顯示名稱 | 定義 | 條件 |
|---|---|---|
| 每日走路步數（頭條） | 只算連續 10 步以上的走路 | — |
| 走路分鐘數 | 走路秒數 ÷ 60 | — |
| 步頻 | 步數 ÷ 走路分鐘數 | — |
| 站立期比例 | 站立時間 ÷（站立＋擺盪） | — |
| 每步時間差異 | 步幅時間的變異係數，直接顯示 %，越小越穩。不換算成分數，避免看起來比資料更精準 | — |
| 左右對稱 | 兩腳平均站立時間，小的 ÷ 大的 × 100% | 兩隻鞋墊、都有指定左右 |
| 雙腳支撐期 | 雙腳同時著地時間 ÷ 走路時間 | 兩隻鞋墊 |

**不顯示步速。**步速要用腳上的動作感測做積分，留給下一期。

### 5.2 三個時間尺度

- **週**：至少有 1 天資料就顯示。頭條是 7 天平均每日步數，圖表是每天的步數。
- **月**：累積滿 7 天才顯示，圖表是最近 4 週的週平均。
- **季**：累積滿 28 天才顯示，圖表是最近 12 週的週平均，小圖是步數、步頻、每步時間差異、左右對稱。
- 不夠的尺度顯示「資料累積中，還要 N 天」，**不放範例數字**。
- 某個指標條件不成立（例如只有一隻鞋墊，沒有左右對稱）就不顯示那一列。

### 5.3 拿掉的東西

- 「穩定／下降／警戒」分期（`GaitPhase`、`phaseSpans`、`phaseBands`）
- 臨床參考步速帶（`referenceSpeed`、`referenceUncertainty`）
- 建議行動（`adviceKeys`）

這幾樣要好幾個月的個人基準才講得出來，「警戒期」這類字眼也碰到健康促進的用詞紅線。說明按鈕（`GaitTopic`）的文案跟著指標調整，沿用「健康促進、不宣稱診斷」的語氣。

### 5.4 跌倒那一列

維持現在的說法（「開啟 App 以來偵測到 N 次跌倒」），不動。

## 6. 功能開關

- 新增 `Constants.realGait`（`--dart-define=REAL_GAIT=on`）和 `realGaitEnabledProvider = Constants.realGait || kDebugMode`，寫法照 `friendsEnabledProvider`。
- **關的時候**（正式版預設）：步態頁維持現在的範例頁與橫幅；`GaitTracker` 不接上，不計算也不存檔。
- **開的時候**：步態頁改讀真資料，`GaitTracker` 接上即時資料流。
- 拿到鞋墊、校正通過後，由使用者決定要不要在正式版打開。

## 7. 測試

### 7.1 現在就做（沒有鞋墊也行）

- **合成波形單元測試**：測試裡產生「已知第幾毫秒落地／離地」的壓力波形，加上雜訊與不規則取樣間隔，檢查 `StepDetector` 抓回來的事件數與時間誤差。
- **容易誤判的情境**：站著左右換重心、坐著抖腳、鞋墊沒穿（全零）、中途斷線缺資料、通知頻率 20 Hz 與 50 Hz 都要過。
- `BoutFilter`：9 步不算、10 步算；段落中間停 3 秒會切成兩段。
- `DailyGaitAccumulator`：跨午夜、多天合併後的變異係數要跟逐筆計算一致。
- **整合測試**：把 `assets/foot-pressure-heatmpt-samples/synthetic_walk_pair_30s.json` 從頭跑到尾，只確認整條線接得通、有數字出來，**不當準確度依據**。
- 步態頁 widget 測試：資料不夠時顯示「累積中」、只有一隻鞋墊時不顯示左右對稱、開關關閉時是範例頁。

### 7.2 拿到鞋墊之後（校正）

- debug 版加「錄原始資料」：把平均之前的原始樣本、手機時間、`soleKey`、`footSide` 存成 JSON，用既有的 `createFileAndShare` 分享出來。正式版看不到。
- 重播工具 `tool/gait_replay.dart`：讀錄製檔，跑整條步態管線，印出每段的步數與指標。
- 錄製腳本（另寫一頁給團隊）：數著走 100 步、坐 2 分鐘、站著換重心 1 分鐘、上下樓梯一趟，雙腳各錄一次。
- **過關標準（使用者可改）**：走路步數誤差 5% 以內；坐、站各段誤判不超過 3 步。
- 如果手機時間誤差太大、站立時間不準，再評估改用韌體錄製資料流（自帶時間戳），這次不做。

## 8. 這次不做

- 步速、步長
- 資料上雲、家屬端
- AI 模型、白話週報
- iOS 背景計算（現有背景藍牙只有 Android；iOS 只在 App 開著時算）
- 分期、警示、建議

## 9. 風險

- **沒有真人資料**：門檻全是初始值，正式版開關關著直到校正通過。
- **手機時間誤差**：藍牙會把幾筆通知擠在一起送到，時間誤差幾十毫秒。步數、步頻不受影響，站立時間、雙腳支撐期會比較粗。
- **單隻鞋墊的步數是估的**（落地次數 × 2），左右不對稱的人會有誤差，頁面說明要寫清楚。
